# Runtime feed publication and recovery

The website reads accepted runtime X and YouTube snapshots from a private Cloudflare feed coordinator. Ordinary source updates publish without a website deployment. The coordinator owns one SQLite-backed Durable Object per feed. Metadata, playback state, content version and refresh health commit atomically. Independent lane generations prevent obsolete ingestion or playback completions from overwriting newer accepted work.

Master Library and Broadcast Titles in the existing Master Link List remain the X authorities. Intake reads bounded standard CSV exports, resolves columns by validated names, normalizes canonical X identities, merges episode aliases, and requires verified title mappings. It preserves every accepted identity and the six legacy archive records. Empty, malformed, ambiguous and unexpectedly reduced candidates retain the last accepted snapshot. The CLI shares this validator, prints a diff, locks generation, and atomically renames a completely validated file. Identical runs preserve file bytes and modification time.

The archive retains external-only Spaces and unavailable broadcasts. Available video replays play through the existing same-origin media proxy. Home tries up to five newest video candidates and confirms advancing media time and nonzero video dimensions. A visitor's active selection remains pinned through refresh. Autoplay denial offers a play button. Failed candidates can retry on the next successful poll.

X metadata runs every ten minutes in the coordinator. The website's existing ten-minute cron calls the private playback lane. YouTube RSS refresh runs separately every five minutes. Each job records its own attempt, success, failure streak and category. Per-ID playback resolution timestamps expose stale retained URLs. A missed refresh interval eventually produces degraded health even when no failed attempt was recorded.

The coordinator preserves successful playback URLs during upstream failure. YouTube validates the official channel and all entries, includes public videos and Shorts, and retains its last verified feed through outages. The optional Data API fallback requires both an opt-in setting and a restricted server secret. Its key travels in a provider header. The public APIs contain no credential values.

Public APIs retain their original item fields and expose version and health. `/api/feed-health` is read-only. The website reads the current owner version before looking up internal cache content, then attaches current health even on cache hits. Public feed responses use `no-store`. Visible clients poll every60seconds. The acceptance window is120seconds from accepted publication to visibility, with source ingestion lag reported separately.

The coordinator has no public route, workers.dev URL or version-preview URL. The website forwards only fixed read paths from public APIs. Private manual refresh supports staging while scheduled jobs remain disabled. A local operator bootstrap relay warms all three lanes and validates both feeds before cutover. It binds to loopback, requires an operator header, rejects cross-origin browser requests, and is never deployed.

Production retains its original KV namespace for rollback. New feed jobs write only their own Durable Object namespace. The website Worker has no Durable Object migration, so its recorded pre-release version remains a rollback target. Preview uses separate Worker/service/DO names and no production KV binding. See recovery/RELEASE.md for executable staging and release steps.
